# Windows 应用软件安装器

核心技术：.NET AOT + YY-Thunks（鸭床）

## 核心原理

采用 .NET AOT + YY-Thunks 技术，将 C# .NET 编写的安装包程序构建为一个无环境依赖的可执行文件。通过 YY-Thunks 技术，可以在低至 Windows XP 的系统上运行。再添加 VC-LTL 库，即可实现脱离 VC++ 运行时环境的依赖，完全支持单个文件运行。

安装包的制作分为两个大的部分的路线：

1. 带 Boost 的方式，入口程序为极简的 .NET 控制台程序，无任何 UI 框架引用依赖。
2. 非 Boost 的方式，直接将安装包 UI 带到入口程序中。

具体而言：

**带 Boost 的方式**：

带 Boost 的方式是制作一个极简的 .NET 控制台程序作为安装包的入口程序，此入口程序就被称为 Boost 程序。然后再制作独立的安装包 UI 程序，将安装包 UI 程序以及准备安装的文件内容打包到 Boost 程序。安装过程中，先进入 Boost 程序，进行通用且必要的环境检查和准备工作，随后再解压出来安装包 UI 程序并运行它，最后由安装包 UI 程序完成安装的剩余工作。

采用 Boost 的方式的好处在于，Boost 程序可以做到极小且极简，且可以复用同一个 Boost 程序来打包不同的安装包 UI 程序。由于 Boost 程序可以处理好环境问题，所以安装包 UI 程序可以专注于安装逻辑和 UI 界面的实现，对所挑选的 UI 框架没有任何限制，可以使用 WinForms、WPF、AvaloniaUI、MAUI 等等。

但与此同时，也带来缺点是需要将 UI 拆分为独立的进程，安装过程也涉及较长的安装包 UI 程序的解压和启动时间。这对于某些杀毒软件来说，可能会让杀毒软件不开心，安装过程比较复杂。如果某个小的应用程序，刚好可以将自己的主程序通过传入命令行参数决定显示为安装包界面，那就可以将安装包 UI 程序集成到主程序中，如此可以让总安装时间不变且此过程都在开发者熟悉的领域内完成。

通常而言，如果主体程序采用的是 WPF UI 框架，那么采用 Boost 的方式会是一个不错的选择。

**非 Boost 的方式**：

非 Boost 的方式是将安装包 UI 程序直接作为入口程序，不再使用独立的 Boost 程序。这样可以让安装包 UI 程序直接运行，省去了解压和启动安装包 UI 程序的时间，安装过程会更快一些。但要求所使用的安装包 UI 框架必须支持 AOT 构建，且能够进行完全 AOT 单文件发布。目前，最符合条件的 UI 框架是 WinForms 框架，比较符合条件的还有 AvaloniaUI 框架

现在安装包的主竞争对手还是 NSIS 和 Inno Setup 这些，其实用 WinForms 就完全能够做到碾压的界面制作优势了。但 AvaloniaUI 框架可以做到更卷的程度，只需要将 AvaloniaUI 所需的 libHarfBuzzSharp.dll 和 libSkiaSharp.dll 文件带到安装包里，在执行 Avalonia UI 框架之前，先将这两个 DLL 文件解压到临时目录并加载它们，就可以让安装包 UI 程序运行起来。再或者是采用静态链接的方式，将这两个 DLL 文件静态链接到安装包 UI 程序中，这样就可以做到完全单文件运行。

采用非 Boost 的方式的好处在于，安装包 UI 程序直接作为入口程序，可以让安装过程更快一些，且安装包 UI 程序的开发和调试都在一个进程内完成，更加方便。

但缺点在于，安装包 UI 程序必须要关注 AOT 兼容性问题，且需要处理好单文件运行时的资源内容依赖引用问题。对于安装包 UI 程序的开发者来说，要求会更高一些。资源内容依赖引用问题，指的是安装包 UI 程序如果使用了某些资源文件（比如图片、图标、XAML 文件等等），这些资源文件在非单文件发布的时候，通常都是放在相对于当前的 exe 的路径，但是在进行单文件发布时，就需要将这些资源文件转换为嵌入程序集资源，用到之前需要手动提取出来，否则程序运行时会找不到这些资源文件而报错。

总体来说就是采用 带 Boost 的方式，可以让安装包 UI 程序的开发者不需要关注多少安装包的特殊要求，比如 AOT 或资源内容依赖引用问题，对安装包 UI 程序的开发者要求较低。而采用 非 Boost 的方式，则可以减少总体复杂度，让安装过程更快一些，但需要安装包 UI 程序的开发者关注更多的细节问题，包括 AOT 兼容和单文件带来的资源内容依赖问题

## 安装包基础知识

### PE Overlay 打包技术

安装包制作的核心技术是 PE Overlay 打包技术。PE Overlay 技术是利用 Windows 可执行文件（PE 文件）格式的一个特性：Windows 可执行文件在文件末尾可以附加任意数据，这些数据不会影响可执行文件的运行。利用这个特性，可以将安装包程序和需要安装的文件内容打包到一个单独的可执行文件中。

简单而言，就是在可执行文件的末尾附加一个压缩包，压缩包内包含安装包程序和需要安装的文件内容。安装包程序在运行时，会先读取自身文件末尾的压缩包内容，解压出安装包程序和需要安装的文件内容，然后运行安装包程序，完成安装过程。

这个过程对签名友好，且强烈要求进行签名。这是因为签名的时候，会将签名信息附加到可执行文件的末尾。即先对安装包可执行文件添加 Overlay 安装包内容，然后再进行签名。这样，签名信息就会附加到 Overlay 内容的末尾，确保杀毒软件认为安装包是可信的。反之，未经签名的安装包，会由于在 PE 附加 Overlay 内容，被大部分杀毒软件所认为文件被篡改，不受信任。再加之安装包安装过程，本身就会进行解压出其他可执行的文件、修改注册表、添加快捷方式等行为，这更是杀毒软件重点关注的行为。
